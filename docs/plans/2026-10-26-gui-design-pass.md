# Plan: GUI design pass on the pre-alpha app (six slices)

> Plan for the design pass over the Tauri + Svelte app built by #96, #97 and
> #98. Governing documents: `docs/design/gui-ux.md` (the screens, flows,
> states and the theme bridge of §7), `docs/plans/2026-10-24-gui-ux-grill-decisions.md`,
> ADR-0002 (two-layer development model), CONTRIBUTING.md "Sandbox-complete
> and hardware-bound issues". Grilled in chat on 2026-10-26. Status:
> **approved in chat on 2026-10-26**; this file is [#103](https://github.com/qubernetic/keyvo/issues/103),
> the slices are #104 to #109.

## 1. Why

The owner's first look at the Profiles screen (epic/34-pre-alpha at 2e3409b,
in the GNOME runtime) found the page preview clipped at its third column,
the editor column's scroll bar drawn over the Name and Accent inputs, and
the screen as a whole visually unacceptable. The same session found that
the app cannot reach the host daemon from inside a Flatpak sandbox at all:
the peer-credential check of `keyvo_client::open` (11f9f19) reads pid 0
through the sandbox's pid namespace and rustix reports it as an error. The
Flatpak runtime is the product path (M4b-1), so both have to be fixed before
M4b, and the layout needs a method that is faster than rebuilding the Tauri
shell for every attempt.

The method: run the real Svelte app on the Vite dev server in a host browser
against an in-memory mock of the daemon, iterate there with the impeccable
skill (critique, prototype variants, live mode), then verify in the GNOME
runtime where the WebKitGTK rendering differs.

## 2. Outcome

- The app in a Flatpak sandbox connects to a daemon on the host.
- `just app-dev` serves the app at `http://localhost:1420` with mock data
  (`VITE_KEYVO_MOCK=1`), four measured theme token sets, and a trace that
  moves; `npm run build` without the variable is unchanged.
- `docs/PRODUCT.md` and `docs/DESIGN.md` exist and a critique of the shell,
  Home and Profiles with heuristic scores is recorded under `docs/design/`.
- The Profiles screen is rebuilt after one of three prototyped variants, with
  the clipped preview and the scroll bar fixed; Home follows in the same
  language. No colour, font or radius outside the §7 tokens.

### Slice 1: pid 0 in the peer check

Files: `crates/keyvo-client/src/client.rs` (`open`, a `peer_uid` helper over
the raw `ucred`), `crates/keyvo-client/Cargo.toml` only if a rustix feature
is missing, `SECURITY.md`, `docs/socket-api.md`.

Proof:

- `just test`: new unit tests in `client.rs`: `peer_uid` on a socket pair
  returns the test's own uid; `check_peer` unchanged; a test that connects
  from a child started with `unshare --user --pid --fork` (skipped with a
  message when `unshare` is unavailable or refused) succeeds against a
  listener in the parent.
- `just lint`, `just fmt-check`, `just deny` green.
- The error text for a foreign uid is unchanged (`refusing the keyvo socket at ...: the process listening on it runs as uid ...`).

User test (owner, host): daemon on the host, app started with
`~/keyvo-prealpha-2026-10-25/keyvo-app-flatpak.sh`; Home shows the device
connected and the mirror; `bin/keyvo ctl status` run inside
`flatpak run --filesystem=host --filesystem=xdg-run/keyvo --command=sh org.gnome.Platform//51`
prints the status reply.

### Slice 2: mock daemon and themes

Files: `app/src/lib/mock/{daemon,profiles,editor,themes,data}.ts`,
`app/src/main.ts` (mount with the mock under `VITE_KEYVO_MOCK=1`),
`app/vite.config.ts` (serve `tests/protocol-fixtures/` and the snapshot PNGs
as static assets in mock mode through `server.fs.allow`), `justfile`
(`app-dev`: host recipe, `npm run dev` with the variable; refuses in native
mode like `run`), `.gitignore` (`.impeccable/`), `docs/design/gui-ux.md`
(§7: the four measured token sets as a table with their sources and
measurement date), CONTRIBUTING.md (one paragraph: the mock dev server and
when to use it), CLAUDE.md (the recipe line).

Mock behaviour: `status` from the fixture with `connected: true` and the
reported geometry; `tiles` returns the snapshot PNGs mapped to keys (empty
keys get the background snapshot); `outline`, `profile_list`, `profile`,
`key` from the parsed TOML; `edit_profile` and `edit_key` mutate the
in-memory profiles and return the edited view the way the daemon does;
`open_profile` is a no-op that logs; `press` returns a trace record for the
key's action; `subscribe` replays the fixture's trace events every two
seconds and emits a `view` change when the mock's focus toggles between
`konsole`, `vscode` and no match every ten seconds. `?theme=` picks the
token set; `?mock-error=unreachable` makes `status` reject so the Home
error state can be designed.

Proof:

- `just app-test`: new vitest files cover the mock against the shared
  fixtures (every reply parses with `parseServerMessage`, the edited views
  match `tests/protocol-fixtures/editor/steps.json`), svelte-check clean.
- `just app-build`: `dist/` without the variable has no mock module (grep
  the bundle for `lib/mock`).
- `just -n app-dev` prints `VITE_KEYVO_MOCK=1 npm run dev`;
  `AGENT_HORDE=1 just app-dev` refuses with the native-mode line.

User test (owner, host): `just app-dev`, open `http://localhost:1420`,
Home shows the mirror with tiles and a trace entry arriving every two
seconds; `?theme=breeze-light` renders light; Profiles lists the three
profiles and an edit of the Global accent changes the preview.

### Slice 4: three Profiles variants

The prototype skill's sub-shape A: `Profiles.svelte` renders `VariantA`,
`VariantB`, `VariantC` on the existing screen behind `?variant=`, with the
floating switcher, in the real shell with the mock. Variants are
structurally different (information hierarchy, where the key editor lives,
how the preview scales). The owner picks in the browser; the decision and
its reasons go into `docs/design/gui-ux.md` §3 (Profiles). User test: the
owner's choice, recorded in the PR.

### Slice 5: Profiles after the chosen variant

The chosen variant becomes the screen, the others and the switcher are
deleted. The preview scales to its column (CSS transform of the 480x480
panel or tiles sized from the column width, never clipped, device
proportions kept); the scroll bars of every scrolling column get a reserved
gutter and the theme's thin style; the key editor's place follows the
variant. `/impeccable polish` and `/impeccable harden` at the end. Proof:
`just app-test` green with updated component tests. User test in the GNOME
runtime at 1363x798 and at the smallest width the shell supports: no
clipped preview, no control under a scroll bar, light and dark.

### Slice 6: Home after the Profiles language

The same round for Home (status strip, mirror, key editor, trace drawer),
keeping the two screens consistent. Same proof and User test shape.
